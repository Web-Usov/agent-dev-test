# Спецификация: Task Manager MVP

## Статус

Готово к реализации при сохранении зафиксированных допущений.

## Связанный Issue

#1

## Контекст

Нужно создать первую рабочую версию небольшого web-приложения для управления личными задачами. Репозиторий пока содержит только development workflow и не имеет продуктового кода.

## Цель

Пользователь должен получить минимальное законченное приложение, в котором можно создать задачу, увидеть её в общем списке, отредактировать, изменить статус и удалить. Данные должны сохраняться в PostgreSQL и быть доступны через backend на NestJS.

## Scope

В MVP входят:

- создание задачи;
- просмотр всех задач;
- редактирование задачи;
- изменение статуса задачи;
- удаление задачи с подтверждением на UI;
- поиск по названию и описанию;
- фильтрация по статусу и приоритету;
- необязательный срок выполнения;
- визуальное отображение статуса и приоритета;
- состояния loading/empty/error на frontend;
- валидация пользовательского ввода;
- сохранение данных в PostgreSQL.

## Не входит в scope

- регистрация, авторизация и пользователи;
- роли и права доступа;
- проекты, команды, списки и теги;
- комментарии и вложения;
- уведомления;
- realtime/WebSocket;
- drag-and-drop Kanban;
- история изменений;
- soft delete/архив;
- pagination/infinite scroll;
- production hosting.

## Пользовательские сценарии

### Сценарий 1 — создание задачи

**Как** пользователь  
**Я хочу** быстро создать задачу  
**Чтобы** сохранить то, что мне нужно сделать.

### Сценарий 2 — просмотр и поиск

**Как** пользователь  
**Я хочу** видеть свои задачи и отфильтровать их  
**Чтобы** быстро найти актуальную работу.

### Сценарий 3 — обновление задачи

**Как** пользователь  
**Я хочу** изменить текст, приоритет, срок или статус задачи  
**Чтобы** поддерживать список в актуальном состоянии.

### Сценарий 4 — завершение задачи

**Как** пользователь  
**Я хочу** перевести задачу в состояние DONE  
**Чтобы** явно видеть выполненную работу.

### Сценарий 5 — удаление задачи

**Как** пользователь  
**Я хочу** удалить ненужную задачу после подтверждения  
**Чтобы** список не засорялся.

## Модель задачи с точки зрения продукта

- `id` — уникальный идентификатор;
- `title` — обязательное название, 1–200 символов;
- `description` — необязательное описание, до 5000 символов;
- `status` — `TODO`, `IN_PROGRESS` или `DONE`;
- `priority` — `LOW`, `MEDIUM` или `HIGH`;
- `dueAt` — необязательный срок выполнения;
- `createdAt` — дата создания;
- `updatedAt` — дата последнего изменения;
- `completedAt` — дата последнего перевода в `DONE`, иначе `null`.

Значения по умолчанию при создании: `status=TODO`, `priority=MEDIUM`.

## Функциональные требования

- FR-1: пользователь может создать задачу с обязательным `title`.
- FR-2: пользователь может получить список всех задач.
- FR-3: пользователь может искать задачи по `title` и `description` без учёта регистра.
- FR-4: пользователь может фильтровать список по `status` и `priority`.
- FR-5: пользователь может открыть и изменить существующую задачу.
- FR-6: пользователь может менять статус задачи между `TODO`, `IN_PROGRESS` и `DONE`.
- FR-7: при переводе в `DONE` система устанавливает `completedAt`; при возврате из `DONE` очищает его.
- FR-8: пользователь может удалить задачу после подтверждения в UI.
- FR-9: frontend показывает понятные loading, empty и error состояния.
- FR-10: некорректные входные данные не сохраняются и возвращают понятную ошибку.

## Нефункциональные требования

- NFR-1: frontend и backend написаны на TypeScript.
- NFR-2: backend использует NestJS.
- NFR-3: постоянное хранилище — PostgreSQL.
- NFR-4: локальный PostgreSQL поднимается воспроизводимо через Docker Compose.
- NFR-5: приложение должно корректно работать на современных desktop и mobile браузерах.
- NFR-6: API должно быть документировано через OpenAPI/Swagger.
- NFR-7: lint, tests и build должны выполняться в CI.
- NFR-8: секреты и реальные credentials не хранятся в репозитории; предоставляется `.env.example`.

## Критерии приёмки

- [ ] AC-1: после запуска локального окружения пользователь открывает web UI и видит список задач или empty state.
- [ ] AC-2: задача с валидным названием создаётся через UI и остаётся после перезагрузки страницы.
- [ ] AC-3: пустое название и название длиннее 200 символов отклоняются.
- [ ] AC-4: пользователь может изменить название, описание, приоритет и срок задачи.
- [ ] AC-5: пользователь может последовательно переводить задачу между всеми тремя статусами.
- [ ] AC-6: перевод в `DONE` заполняет `completedAt`, возврат из `DONE` очищает его.
- [ ] AC-7: фильтры по статусу и приоритету могут применяться одновременно.
- [ ] AC-8: поиск находит совпадения в названии и описании без учёта регистра.
- [ ] AC-9: удаление требует подтверждения и после подтверждения задача исчезает из БД и UI.
- [ ] AC-10: неизвестный `id` возвращает 404, невалидный payload — 400.
- [ ] AC-11: Swagger/OpenAPI описывает task endpoints и DTO.
- [ ] AC-12: обязательный CI успешно выполняет lint, tests и build для backend и frontend.

## Граничные случаи

- пустая строка и строка только из пробелов как `title`;
- одновременное применение поиска и нескольких фильтров;
- срок выполнения в прошлом разрешён и отображается как просроченный;
- повторное сохранение задачи без фактических изменений;
- удаление или изменение уже несуществующей задачи;
- перевод `DONE → TODO/IN_PROGRESS`;
- ошибки сети/API на frontend.

## Ограничения

- первая версия однопользовательская;
- backend предоставляет REST API;
- frontend — отдельное SPA;
- production deployment не является частью задачи.

## Допущения

- отсутствие авторизации в MVP допустимо;
- React + Vite + TypeScript подходит для первой версии frontend;
- Prisma подходит как ORM/миграционный слой для PostgreSQL;
- для ожидаемого объёма персональных задач pagination пока не требуется.
