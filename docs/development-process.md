# Процесс разработки

Этот документ описывает рекомендуемый цикл облачной разработки через ChatGPT.com + GitHub.

## 1. Инициирование работы

Новая функция обычно начинается с Issue. Issue должен отвечать на три вопроса:

- какую проблему решаем;
- для кого она важна;
- как поймём, что задача выполнена.

Для бага указываются воспроизводимость, фактическое и ожидаемое поведение.

После получения задачи агент выбирает **один базовый workflow skill** из `.agents/skills/`:

- `dev-core` — новая или недостаточно определённая функция, изменение требований, scope или архитектуры;
- `dev-build` — реализация уже согласованного решения;
- `dev-debug` — баг, regression, failing test или CI failure;
- `dev-review` — независимая проверка реализации/PR.

Явно указанный пользователем workflow skill имеет приоритет над автоматическим выбором.

## 2. Auxiliary skills

Workflow skill задаёт **процесс работы**, а специализированные capability skills задают предметную экспертизу.

Перед существенной работой агент:

1. определяет необходимые компетенции;
2. просматривает metadata доступных в текущей среде auxiliary skills (`name` и `description`), если среда их предоставляет;
3. выбирает минимальный релевантный набор;
4. применяет только выбранные skills.

Пользователь не обязан вручную перечислять frontend/backend/testing skills для каждой задачи. Набор auxiliary skills не фиксируется в шаблоне и может отличаться между Codex, ChatGPT Web и конкретным проектом.

## 3. Clarification и спецификация — `dev-core`

Для новой или неоднозначной функции сначала используется `dev-core`.

Clarification должен спрашивать пользователя только о решениях, которые существенно меняют пользовательское поведение, публичные контракты, данные, безопасность, архитектуру, acceptance criteria или scope. Локальные обратимые решения допускается принимать как явные assumptions.

Для функциональности создаётся каталог `specs/<NNN>-<slug>/` на основе `specs/_template/`.

Минимальный набор:

- `spec.md` — что и зачем строим;
- `plan.md` — как строим;
- `tasks.md` — конкретные шаги реализации.

### `spec.md`

Содержит:

- контекст и проблему;
- цели;
- что не входит в scope;
- пользовательские сценарии;
- функциональные и нефункциональные требования;
- критерии приёмки;
- assumptions и открытые вопросы.

Технические детали здесь минимальны.

### `plan.md`

Содержит:

- выбранную архитектуру;
- затрагиваемые модули;
- изменения данных/API;
- стратегию тестирования;
- observability/diagnostics;
- риски и миграции;
- при необходимости ADR.

### `tasks.md`

Задачи должны быть достаточно малы, чтобы результат каждой можно было проверить.

До реализации `dev-core` проверяет согласованность:

- покрывает ли plan все требования spec;
- есть ли task для каждого существенного пункта plan;
- нет ли задач, не объяснённых spec/plan;
- определён ли способ проверки критериев приёмки.

Готовый результат `dev-core` имеет статус `READY FOR IMPLEMENTATION`.

## 4. Реализация — `dev-build`

Рекомендуемая модель веток:

- `feat/<issue>-<slug>`;
- `fix/<issue>-<slug>`;
- `chore/<issue>-<slug>`.

`dev-build` читает constitution, spec, plan, tasks и релевантные ADR, затем реализует решение небольшими проверяемыми шагами.

После значимых изменений запускается:

```bash
bash scripts/ci
```

Для существенных, интеграционных/e2e/миграционных изменений используется:

```bash
bash scripts/ci-full
```

Если в ходе реализации обнаружено существенное противоречие требованиям или архитектуре, агент не угадывает решение и возвращается в `dev-core`.

## 5. Диагностика — `dev-debug`

Для бага или неизвестной причины падения применяется `dev-debug`:

```text
symptom → reproduction → evidence → root cause → minimal fix → regression test → CI
```

При падении GitHub Actions агент сначала изучает:

1. упавший workflow/job;
2. конкретный step;
3. полный log;
4. диагностический artifact;
5. только после этого меняет код.

`scripts/diagnostics` собирает безопасный текстовый пакет с контекстом выполнения. Конкретный проект может расширить его через `scripts/project-diagnostics`.

Исправление должно устранять подтверждённую причину, а не только симптом. По возможности добавляется regression test.

## 6. Pull Request

PR должен ссылаться на Issue и spec и содержать:

- что изменено;
- почему решение соответствует plan;
- как проверить;
- результаты CI;
- какие риски/ограничения остались.

Если в ходе реализации потребовалось отойти от plan, сначала обновляется plan/ADR, затем код.

Merge не выполняется агентом без явной команды пользователя.

## 7. CI

### Быстрый CI

Запускается на `push` и `pull_request`. Его задача — быстро ловить типовые ошибки.

Контракт:

```bash
bash scripts/ci
```

### Полный CI

Используется для интеграционных/e2e/миграционных и других тяжёлых проверок.

Контракт:

```bash
bash scripts/ci-full
```

Полный CI также можно запускать вручную через GitHub Actions.

## 8. Review и converge — `dev-review`

Перед merge применяется `dev-review`. По умолчанию это read-only режим: reviewer ищет findings, но не исправляет их сам.

Проверяется:

- выполнены ли acceptance criteria;
- соответствует ли реализация spec/plan/ADR;
- не появился ли незапланированный scope;
- корректны ли публичные контракты и изменения данных;
- тесты действительно защищают новое поведение;
- нет ли security/performance/data regressions;
- актуальны ли tasks/docs/ADR;
- проходит ли CI.

Если finding требует исправления, после review выбирается новый режим:

- `dev-build` — понятное исправление в рамках существующего plan;
- `dev-debug` — требуется расследование причины;
- `dev-core` — требуется изменить требования/scope/архитектуру.

## 9. Merge

По умолчанию рекомендуется squash merge после зелёного обязательного CI и завершённого review.

`main` должен оставаться рабочим состоянием проекта.

## 10. Skills: GitHub, Codex и ChatGPT Web

`.agents/skills/` — канонический version-controlled источник базовых workflow skills.

### Codex

Codex может использовать project skills из `.agents/skills/` и дополнительно обнаруживать локальные/персональные capability skills.

### ChatGPT Web

Файлы `.agents/skills/` в GitHub сами по себе не устанавливают native ChatGPT Skill. Для установки или обновления используется производный bundle:

```bash
bash scripts/package-skills
```

Либо workflow GitHub Actions **Упаковать skills**. Он создаёт artifact с отдельным ZIP на каждый skill. ZIP устанавливается через ChatGPT Skills UI.

Установленная в ChatGPT копия считается производной; source of truth остаётся в GitHub. Автоматическая синхронизация между ними в шаблоне не предполагается.

Registry, версии и правила обновления описаны в `.agents/skills/README.md`.

## 11. GitHub Spec Kit

Шаблон совместим по модели с GitHub Spec Kit, но не зависит от него.

Смысловое сопоставление сохраняется:

- constitution → `docs/constitution.md`;
- specify/clarify/plan/tasks → `dev-core`;
- implement → `dev-build`;
- debugging → `dev-debug`;
- converge/review → `dev-review`.

Официальный Spec Kit можно подключить дополнительно, не форкая его внутренности в этом template repository.

## 12. GitHub Pages

Pages не нужен для разработки приложения и поэтому не включён в обязательный pipeline. Если проекту нужна публичная документация, можно использовать отдельный manual workflow публикации `docs/` через GitHub Pages.

Hosting самого приложения, preview environments, staging и production относятся к отдельному слою инфраструктуры и не входят в этот шаблон.
