# Конституция проекта

Этот документ содержит устойчивые правила проекта. Они важнее локальных решений в Issue и PR.

> При создании нового проекта из шаблона адаптируйте этот файл под продукт и стек. Изменение конституции должно быть осознанным и отражаться в PR.

## 1. Spec-first

Любое изменение пользовательского поведения, публичного API, модели данных, безопасности или архитектуры начинается со спецификации.

Последовательность по умолчанию:

`spec → plan → tasks → implementation → CI → review → converge → merge`.

## 2. GitHub — источник истины

Код, спецификации, ADR, Issue, PR и результаты CI должны позволять восстановить состояние проекта без памяти конкретного чата или конкретного AI-агента.

Решения, влияющие на будущее проекта, нельзя оставлять только в переписке.

## 3. Проверяемость

Каждое существенное изменение должно иметь воспроизводимый способ проверки. Предпочтение отдаётся автоматическим тестам и детерминированным скриптам.

Команды CI должны одинаково работать у человека и в GitHub Actions.

## 4. Малые изменения

Предпочтительны небольшие PR с понятной целью. Один PR не должен без необходимости смешивать функциональность, рефакторинг и инфраструктурные изменения.

## 5. Безопасность по умолчанию

- Минимальные GitHub Actions permissions.
- Никаких secrets в репозитории, логах или artifacts.
- Никакого выполнения произвольных команд из Issue, PR или комментариев.
- Зависимости и внешние actions должны быть осознанными и по возможности зафиксированными по стабильной версии.

## 6. CI — обязательный арбитр

Merge при красном обязательном CI запрещён. Нельзя отключать тест, линтер или проверку только ради прохождения pipeline без объяснения причины и отдельного решения.

## 7. Документация как часть реализации

Изменение считается неполным, если устарели spec, ADR, инструкции или публичные контракты.

## 8. Язык

Документация, Issue и Pull Request ведутся на русском языке. Код, названия сущностей и технические термины могут быть на английском.

## 9. Независимость от конкретного AI

Проект не должен требовать одного конкретного coding agent. `AGENTS.md`, specs, scripts и CI формируют vendor-neutral контракт.

GitHub Spec Kit можно использовать как дополнительный orchestration layer, но проект не должен зависеть от его внутреннего устройства.

## 10. Простота инфраструктуры разработки

GitHub Actions используется для сборки, тестирования, статического анализа, миграционных тестов и диагностик. Он не рассматривается как постоянный runtime приложения или универсальный удалённый shell.

Hosting/staging/production — отдельная архитектурная задача и не должна смешиваться с базовым development workflow без необходимости.
