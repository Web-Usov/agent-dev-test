# dev-debug

Режим расследования дефектов, regressions и падений CI.

## Главный принцип

Не переходи от симптома сразу к случайному изменению кода.

Рабочая цепочка:

```text
symptom → reproduction → evidence → root cause → minimal fix → regression test → CI
```

## Перед началом

1. Прочитай `AGENTS.md`, `docs/constitution.md` и связанные spec/plan/ADR, если они существуют.
2. Зафиксируй фактический симптом и ожидаемое поведение.
3. Определи необходимые предметные компетенции.
4. Просмотри metadata доступных auxiliary skills (`name` + `description`) и выбери минимальный релевантный набор.
5. Для CI failure сначала используй логи, job/step и diagnostic artifact; не изменяй код до первичной локализации причины.

Не проси пользователя вручную перечислять testing/frontend/database skills, если среда уже предоставляет их metadata.

## Workflow

### 1. Воспроизведение

Получить самый маленький стабильный способ воспроизвести проблему:

- failing test;
- конкретный API request;
- минимальный browser flow;
- точный CI job/step;
- детерминированный локальный сценарий.

Если воспроизвести нельзя, собери доступные evidence и явно укажи уровень уверенности.

### 2. Evidence

Собирай только данные, которые помогают отличить гипотезы:

- error/stack trace;
- логи конкретного failing step;
- входные данные;
- diff последнего изменения;
- результаты тестов;
- состояние зависимостей/контрактов.

Не делай широкий dump environment и не выводи secrets.

### 3. Гипотезы и root cause

Сформулируй 1–3 наиболее вероятные гипотезы и проверь их в порядке стоимости/вероятности.

Root cause должен объяснять одновременно:

- почему возникает симптом;
- почему он возникает именно в данных условиях;
- почему предлагаемое исправление устраняет причину, а не маскирует проявление.

### 4. Минимальный fix

Исправляй минимальный необходимый scope. Не используй баг как повод для несвязанного refactoring.

Если root cause показывает ошибку требований/архитектуры, останови изменение и переключись в `dev-core`.

### 5. Regression protection

По возможности добавь тест, который:

1. падает на старом поведении;
2. проходит после fix;
3. проверяет именно root cause или внешний контракт, а не случайную деталь реализации.

### 6. Проверка

Запусти `bash scripts/ci` и при необходимости `bash scripts/ci-full`.

Для CI-specific проблемы повторно проверь тот же workflow/job, если среда это позволяет.

## Выход

В завершении дай краткий отчёт:

- симптом;
- подтверждённый root cause;
- исправление;
- regression test/проверка;
- результат CI;
- оставшиеся риски.

Если root cause не подтверждён, не представляй гипотезу как факт — укажи, какие evidence ещё нужны.
