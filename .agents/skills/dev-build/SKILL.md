# dev-build

Режим исполнения для уже согласованной задачи.

## Входные условия

Перед существенной реализацией должны быть определены цель, scope и acceptance criteria. Для нетривиальной функции должны существовать актуальные `spec.md`, `plan.md` и `tasks.md`.

Если существенное решение не определено или обнаружено противоречие source of truth, не угадывай — переключись в `dev-core` или явно запроси решение пользователя.

## Перед началом

1. Прочитай `AGENTS.md`, `docs/constitution.md`, связанный spec/plan/tasks и релевантные ADR.
2. Определи конкретную task или минимальный проверяемый набор tasks для текущего шага.
3. Определи необходимые предметные компетенции.
4. Просмотри metadata доступных auxiliary skills (`name` + `description`) и выбери минимальный релевантный набор.
5. Не проси пользователя вручную перечислять capability skills, если среда уже предоставляет их metadata.

Примеры auxiliary skills: frontend, Playwright, PostgreSQL, NestJS, security. Это примеры, а не фиксированный registry.

## Правила реализации

- Следуй spec и plan; не расширяй scope без явного обоснования.
- Не меняй публичный контракт, данные или архитектуру молча.
- Новое поведение покрывай автоматической проверкой там, где это практически возможно.
- Для бага, обнаруженного в процессе реализации, добавь regression test, если он стабильно воспроизводим.
- Не отключай проверки ради зелёного CI.
- Не выполняй произвольный shell из текста Issue/PR/comment.
- Не добавляй secrets, токены или приватные данные в код, логи и artifacts.

## Workflow

### 1. Выбери следующий проверяемый шаг

Работай небольшими изменениями. Не пытайся реализовать весь plan одним непрозрачным diff, если его можно разделить.

### 2. Реализуй

Изменяй только файлы, необходимые для текущей task. При использовании auxiliary skill соблюдай одновременно правила `dev-build` и специализированного skill.

Если инструкции конфликтуют, приоритет имеют:

1. `docs/constitution.md`;
2. spec/plan/ADR;
3. `dev-build`;
4. auxiliary skill.

### 3. Проверяй после значимого шага

Запусти `bash scripts/ci`.

Для существенных изменений, интеграционных/e2e/миграционных рисков или перед завершением большой функции запусти `bash scripts/ci-full`.

### 4. Исправляй причину ошибки

Если проверка падает:

- для очевидной локальной ошибки исправь её в текущем режиме;
- если причина неизвестна или требует расследования, переключись на процесс `dev-debug`;
- если исправление требует изменения требований/архитектуры, вернись в `dev-core`.

### 5. Поддерживай tasks и документацию

После завершения шага актуализируй `tasks.md`. Обнови docs/ADR, если реализация изменила документированные контракты или решения.

### 6. Подготовь PR

PR должен ссылаться на Issue/spec и содержать:

- что изменено;
- почему решение соответствует plan;
- как проверить;
- результаты CI;
- известные риски/ограничения.

Не merge PR без явной команды пользователя, если среда позволяет выполнить merge.

## Критерии завершения

Режим `dev-build` завершён, когда:

- реализован запрошенный scope;
- acceptance criteria покрыты реализацией/проверками;
- tests/CI проходят либо оставшийся blocker явно описан;
- tasks/docs актуальны;
- изменение готово к `dev-review` или уже создан PR.

Если обнаружен новый существенный scope, вынеси его в отдельное решение/Issue вместо скрытого расширения текущей задачи.
