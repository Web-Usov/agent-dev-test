# dev-core

Главный режим для превращения идеи или неоднозначной задачи в согласованную спецификацию и план реализации.

## Не использовать

Не использовать как основной режим для:

- реализации уже согласованного `spec/plan/tasks` — используй `dev-build`;
- воспроизводимого бага или падения CI — используй `dev-debug`;
- независимого review готового изменения — используй `dev-review`.

Если пользователь явно указал другой workflow skill, его выбор имеет приоритет.

## Перед началом

1. Прочитай `AGENTS.md` и `docs/constitution.md`.
2. Найди связанный Issue, существующий spec, plan, tasks и релевантные ADR.
3. Изучи существующие контракты/код только настолько, насколько это нужно для корректного scope и технического плана.
4. Определи необходимые предметные компетенции и оцени metadata доступных auxiliary skills (`name` + `description`).
5. Подключи только минимальный набор вспомогательных skills, который существенно улучшает результат.

Не требуй от пользователя вручную перечислять frontend/backend/testing skills, если среда уже предоставляет их metadata.

## Clarification policy

Задавай вопрос пользователю только если неизвестность существенно меняет хотя бы одно из:

- пользовательское поведение;
- публичный API/контракт;
- модель данных или миграцию;
- безопасность/права доступа;
- архитектуру или необратимое решение;
- acceptance criteria;
- scope и стоимость задачи.

Для локального, обратимого или стандартного решения сделай разумное assumption и явно запиши его в spec/plan.

Не задавай длинную анкету. Группируй только блокирующие вопросы и продолжай работу после ответа.

## Workflow

### 1. Сформулируй problem statement

Зафиксируй:

- какую проблему решаем;
- для кого;
- какой результат нужен;
- что сейчас мешает.

### 2. Установи границы

Сформируй краткий scope contract:

- цель;
- in scope;
- out of scope;
- acceptance criteria;
- ограничения;
- assumptions;
- открытые блокирующие вопросы.

### 3. Создай или обнови spec

Используй `specs/_template/spec.md` и существующие правила проекта.

Spec описывает **что и зачем**, а не детали реализации.

### 4. Создай или обнови plan

Plan должен покрывать каждое существенное требование spec и определить:

- архитектуру;
- затрагиваемые компоненты;
- данные/API/миграции;
- тестовую стратегию;
- observability/diagnostics;
- риски и security;
- необходимость ADR.

Если выбор зависит от специализированной области, используй релевантный auxiliary skill, если он доступен.

### 5. Создай или обнови tasks

Каждая task должна быть небольшой, проверяемой и привязанной к plan. Не добавляй work, который нельзя объяснить spec/plan.

### 6. Проверь согласованность

Перед завершением проверь:

- каждый acceptance criterion покрыт plan/tasks;
- нет скрытого scope;
- assumptions записаны;
- способ проверки результата определён;
- ADR создан, если решение соответствует ADR-триггерам проекта.

## Выход

В конце явно сообщи один из статусов:

- `READY FOR IMPLEMENTATION` — можно переходить к `dev-build`;
- `BLOCKED` — перечисли только блокирующие вопросы/зависимости;
- `NEEDS DECISION` — требуется решение пользователя по существенной развилке.

Не начинай существенную реализацию кода в `dev-core`, если пользователь отдельно не попросил сменить режим.
